# Методика ЕГ — T4: концептуальные макеты S01–S10

Статус: **CONCEPTUAL UI / NO-CODE / ILLUSTRATIVE**

Макеты показывают информационную архитектуру будущего решения и не означают обязательную программную реализацию. Канонический стиль: светлая рабочая область, тёмный sidebar, синие акценты, белые карточки, сдержанный B2B.

## S01 — Дашборд

Назначение: управленческая сводка.

```text
┌ Sidebar ┐  ДАШБОРД
│S01      │  [Новые] [C3/C4 open] [SLA] [Verified resolution]
│S02      │
│...      │  Динамика отзывов        Критичность C1–C4
│S10      │  ────────────────         ───────────────
│         │  Топ аспектов             Просроченные мероприятия
└─────────┘  Response rate ≠ Resolution rate
```

Evidence: T3 P6/P7; KPI-01, 06, 12, 16.

## S02 — Список отзывов

Колонки: case ID, дата, источник, рейтинг/тональность, аспекты, C-level, статус, владелец, срок.

Фильтры: период, канал, аспект, C1–C4, статус, просрочка, магазин/точка.

Evidence: P1/P2/P3/P6.

## S03 — Карточка отзыва

Блоки:
- исходный текст + provenance;
- source URL/ID;
- тональность;
- multi-label аспекты;
- C1–C4 и причина;
- screening vs expert verified;
- история статусов;
- связанные решения/ответы/мероприятия/outcome.

Ключевой UX: исходные данные визуально отделены от аналитической интерпретации.

## S04 — Импорт / получение

Блоки:
- источник;
- дата загрузки;
- mapping полей;
- количество raw/accepted/excluded/duplicates;
- ошибки качества;
- provenance completeness;
- обезличивание.

Evidence: acquisition T3 + P1/P2.

## S05 — Решения

Реестр решений: case, decision type, rationale, responsible role, C-level, target due, status.

Отдельные признаки: `response required`, `action required`, `legal review required`.

## S06 — Карточка решения

```text
Кейс PXR-XXXX / C3
Основание решения: ___________________
Ответ клиенту: [не требуется / подготовить / отправлен]
Мероприятие:   [создать / в работе / завершено]
Владелец: ____   Срок: ____
Эскалация: ____
Outcome: [не проверен]
История/Audit: _______________________
```

Evidence: P3/P7/P8; P4 как проектный principle.

## S07 — Контроль

Очереди:
- просрочено;
- C3/C4 без expert verification;
- ответ отправлен, мероприятие не завершено;
- мероприятие завершено, outcome не проверен;
- reopened cases.

Evidence: P7; P5 как проектное требование.

## S08 — Аналитика

Разделы:
- динамика;
- каналы;
- рейтинг/тональность;
- аспекты;
- C1–C4;
- aspect×criticality;
- response vs verified resolution;
- repeat problems;
- drill-down до исходного кейса.

Evidence: P6; T3 factual tables.

## S09 — Справочники

Редактируемые сущности:
- аспекты;
- critical triggers;
- C1–C4 definitions;
- роли;
- decision/action/outcome types;
- SLA targets;
- source groups.

Любое изменение codebook имеет версию и дату вступления.

## S10 — Настройки / методика

Блоки:
- активная версия codebook;
- правила обезличивания;
- mapping каналов;
- RACI mapping на реальные должности организации;
- KPI definitions;
- evidence/audit policy;
- экспорт методики/отчёта.

## Навигационная логика

`S01 → S02 → S03 → S05/S06 → S07 → S08`

`S04` обслуживает вход данных, `S09–S10` — методическую настройку.

## Общие UX-правила

1. C4 визуально выделяется, но не означает подтверждённое нарушение до verification.
2. `Response sent` и `Resolved` всегда разные состояния.
3. На S03 всегда виден provenance.
4. Аналитика S08 допускает drill-down до исходных кейсов.
5. Пользователь должен видеть, какая метка rule-based, а какая expert verified.
6. Макеты являются приложением/иллюстрацией проектной концепции, а не evidence фактической реализации.
