# FeedbackPro — master-реестр требований ВКР

Статус: **MASTER / SOURCE-OF-TRUTH**.

Этот документ является единым реестром проектных требований FeedbackPro. Он формализует утверждённые требования ВКР и продукта. Точные номера страниц нормативного документа не выдумываются: если в GitHub отсутствует исходный нормативный PDF/экстракт, ссылка фиксируется на уровне утверждённого требования проекта до переноса первичного источника.

## 1. Требования ВКР

| ID | Требование | Проверка |
|---|---|---|
| VKR-G1-001 | Тема ВКР не меняется без отдельного утверждения | A0 baseline |

| VKR-G1-003 | Не выдумывать фактические результаты, источники, KPI и апробацию | review/evidence |
| VKR-G2-001 | Описать AS-IS процесса работы с отзывами | текст ВКР/evidence |
| VKR-G2-002 | Выявить проблемы существующего процесса | текст ВКР |
| VKR-G2-003 | Определить измеримые показатели процесса и результата | methodology/KPI |
| VKR-G2-004 | Использовать эмпирический корпус отзывов | dataset manifest |
| VKR-G3-001 | Разработать самостоятельное программное решение FeedbackPro | executable/tests |
| VKR-G3-002 | Реализовать системную обработку отзывов | E2E gate |
| VKR-G3-003 | Обеспечить воспроизводимость и прослеживаемость анализа | version/audit |
| VKR-G3-004 | Обосновать архитектуру, модель данных и алгоритмы | docs/tests |
| VKR-G3-005 | Реализовать переход от анализа к решению и контролю | S05–S07/tests |
| VKR-G3-006 | Реализовать аналитику/отчётность на фактических данных | S01/S08/tests |

| VKR-G3-008 | Подготовить пилотную апробацию и BEFORE/AFTER методику без фиктивных значений | pilot protocol |

## 2. Требования продукта

| ID | Требование |
|---|---|
| FP-SOT-001 | GitHub `repairwtfb3-stack/FeedbackPro` — единственный источник истины |

| FP-ARCH-002 | SQLite — локальное хранилище; миграции неизменяемы задним числом |
| FP-ARCH-003 | Python 3.11+ / PySide6 / QML — базовый стек |
| FP-UI-001 | Каноническая архитектура экранов S01–S10 |
| FP-REV-001 | Импорт CSV/XLSX, нормализация, provenance и dedup |
| FP-AN-001 | Анализ тональности positive/neutral/negative |
| FP-AN-002 | Multi-label анализ тем/аспектов |
| FP-AN-003 | Критичность low/medium/high/critical отдельно от тональности |
| FP-AN-004 | Каждый auto analysis хранит version/explanation |
| FP-DEC-001 | Отзыв может быть связан с управленческим/коммуникационным решением |
| FP-CTRL-001 | Решение проходит контролируемый жизненный цикл до verified |
| FP-KPI-001 | KPI/аналитика вычисляются только из локальных фактических данных |
| FP-REP-001 | Отчёт воспроизводим и не содержит выдуманных BEFORE/AFTER |
| FP-EXP-001 | Экспертная правка хранится отдельно от auto analysis и имеет историю |
| FP-EXP-002 | Контрольная выборка — 300 реальных отзывов, воспроизводимый отбор |
| FP-QUAL-001 | Метрики качества считаются только по фактически размеченным данным |

| FP-DATA-001 | Backup/restore и integrity checks не должны терять данные |
| FP-TEST-001 | A2 regression обязателен для A3 изменений |
| FP-TEST-002 | Gate A3 разрешает `A3 WORK_VERIFIED = YES` только при полном PASS |

## 3. Управление изменениями

Любое новое требование должно получить уникальный ID, источник/обоснование, реализацию, тест и evidence. Изменение frozen baseline выполняется только отдельным change decision и отражается в `TRACEABILITY_MASTER.md`.
